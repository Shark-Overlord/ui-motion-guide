## 新类别如何接入

用户提供新组件参考后，在这个 skill 内新增类别，不另外复制一套通用规则。

1. **核对参考**：确认组件类别、动态成品与静态起点、具体状态/触发方式及来源完整性。静态截图不能证明时序，静态 HTML 不能充当已完成动效。
2. **建立类别决策树**：在 `references/<category>/decision-tree.md` 按该类别的交互目的分支；叶子说明机制、来源、实现条件及类别特有的验收点。根据实际案例拆分，不固定为 10 个叶子。
3. **分离机制和风格**：同类别的不同皮肤放在对应参考下，先选交互机制，再按用户指定的风格选源码。颜色/材质变化不自动变成新的组件类别或新的交互叶子。
4. **保留参考原件**：新增来源可放入 `assets/<category>/<style>/`，按来源记录哈希与路径。现有按钮的 `assets/style-1/` 和参考文件继续使用，不必为了目录统一搬动原件。
5. **注册入口**：在上表加入实际范围、决策树、来源和覆盖状态。`SKILL.md` 只保留组件类别路由和共享约束，不堆入每个类别的完整树。
6. **验证路由与行为**：检查至少一条新类别的典型请求能定位到实际参考，以及一条容易混淆的请求不会误入按钮分支；核对文档引用和来源。实现目标项目时再完成对应运行验收。

叶子 ID 使用类别前缀，如 `buttons/L2`，避免新类别也有 L2 时混淆。按钮现有文件使用短 ID L1–L10；对外说明命中路径时补上 `buttons/`。

## 复合组件和未收录类别

按用户要求修改的对象确定主类别。例如“输入框内清空按钮”若只改按钮反馈，走 buttons；若要联动输入、清空、错误状态及字段布局，需要输入组件类别，不能只用按钮参考声称整个输入组件已覆盖。

复合组件可组合不同类别的叶子，共享同一业务状态。新增类的专有机制不强行改写成按钮逻辑。

类别未收录时，明确说明缺少该类别的成品参考。在总入口已确定的修改范围内，仍可结合目标结构和已有适用机制实现，标明迁移推导；扫描候选尚未得到用户同意时不实施。实现一次不等于自动扩充或注册 skill，只有维护 skill 的请求才写入新类别。
